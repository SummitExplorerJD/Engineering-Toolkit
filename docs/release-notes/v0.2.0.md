# Engineering Toolkit `v0.2.0`

**Status:** Prepared for stable release after final candidate verification.

`v0.2.0` introduces a provider-neutral canonical skill model and a guarded local
lifecycle for skill packages. It does not generate project-specific skills or
synchronize provider-native formats; those capabilities remain planned for
later `v0.2.x` releases.

## Added

- Experimental `engkit.skill/v1alpha1` manifest with explicit identity,
  version, capabilities, inputs, outputs, permissions, compatibility,
  ownership, provenance, and resource integrity.
- Deterministic read-only skill discovery, inspection, and validation.
- Immutable JSON plans for canonical skill creation, update, and removal.
- Exact approval binding for every local skill mutation.
- Transactional `skills create`, `skills update`, and `skills remove` commands.
- Explicit `skills recover` handling for interrupted mutations.
- Durable JSON plans, append-only JSONL journals, atomic JSON checkpoints,
  per-skill locks, staged package verification, and retained recovery backups.
- Accepted architecture for offline skill templates and explicit project
  profiles planned for `v0.2.1`.

## Safety and ownership

- A directory is canonical only when it contains a valid Engineering Toolkit
  manifest. Existing Spec Kit and provider-native skill directories remain
  external and are not adopted or modified implicitly.
- Plans bind complete source and target inventories and content digests.
- Execution rebuilds the plan immediately before accepting its exact full
  `plan_id`.
- Create and update validate a complete staged package before publication.
- Update and remove rename the previous package into same-filesystem recovery
  storage instead of deleting or merging it file by file.
- Recovery verifies persisted evidence and observed digests. Ambiguous content
  is preserved and fails closed.
- Windows reserved names, invalid portable paths, escaping resources, symlinks,
  undeclared resources, and integrity mismatches are rejected.
- Legitimate Windows 8.3 short-path aliases are accepted without weakening
  symbolic-link or junction checks.
- Skill resources are data: no skill command executes scripts, contacts a
  network, accesses credentials, or grants declared permissions.

## Compatibility and upgrade notes

- The canonical skill and mutation schemas remain experimental `v1alpha1`
  contracts.
- Mutation plans generated before execution support was added must be
  regenerated because the executable flag participates in the plan identity.
- Canonical package updates require a higher Semantic Version than the installed
  package.
- Existing `v0.1.1` installations can use the release `install.ps1` or
  `install.sh` with explicit upgrade mode after `v0.2.0` is published.
- New workspace initialization includes ignored `.engkit/recovery/` state.
  Existing initialized workspaces receive only the missing `/recovery/*` ignore
  rule during their first approved skill execution.

## Verification requirements

The stable release must be rebuilt from the reviewed release commit and pass:

- the complete Go test suite and static analysis;
- release packaging and manifest verification;
- native binary and installer transaction tests on Windows, Linux, and macOS;
- AMD64 and ARM64 coverage for all three operating systems;
- independent review of `SHA256SUMS` and `release-manifest.json`; and
- a local upgrade test from the published `v0.1.1` installation.

## Known limitations

- No skill-template scaffold, first-party template catalog, project profile, or
  project composition command is included. These are planned for `v0.2.1`.
- No Codex, Claude Code, or OpenCode skill synchronization is included. It is
  planned after canonical project composition.
- Dependencies declared by a skill are validated as metadata but are not
  resolved or installed.
- Completed update and remove backups are retained until deliberate manual
  maintenance; automatic cleanup is not included.
- Remote skill installation, skill marketplaces, and skill-script execution are
  not included.
- Production TUF activation, automatic updates, self-replacement,
  package-manager distribution, Windows Authenticode signing, and macOS signing
  and notarization remain unavailable.
