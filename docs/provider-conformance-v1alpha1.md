# Provider conformance and pilot validation `v1alpha1`

## 1. Status and approval boundary

This document defines the accepted contract for `v0.2.2D`. The D1 offline
conformance gate is complete: candidate `v0.2.2-rc.2` and stable `v0.2.2`
passed the native six-platform matrix and their portable evidence compared
equal. This boundary does not authorize provider CLI invocation, provider
installation, authentication, network access, credential access, or D2 native
discovery.

Implementation is split into two independently approved gates:

- **D1 — offline conformance harness:** deterministic tests in disposable
  workspaces using the locally built Engineering Toolkit binary; and
- **D2 — native discovery smoke:** bounded checks with installed provider
  runtimes after their exact versions, commands, authentication behavior,
  network behavior, evidence capture, and cleanup are separately reviewed.

Passing D1 proves that generated bytes and lifecycle behavior conform to the
reviewed provider contracts. It does not by itself prove that a particular
provider release discovers or invokes the skill.

## 2. Objective

Validate the immutable `project-guide@0.1.0` pilot, produced by the packaged
`go-service@0.1.0` profile, against the accepted Codex, Claude Code, and
OpenCode adapter contracts without adopting provider-native files or official
Spec Kit content.

The gate must demonstrate:

1. exact and deterministic provider rendering;
2. safe transactional sync and unsync behavior;
3. provider isolation and file-level ownership;
4. preservation of canonical, provider-native, and Spec Kit content;
5. equivalent observable results on every supported release platform; and
6. explicit separation between contract validation and native runtime
   discovery.

## 3. Provider evidence baseline

The accepted adapter contract remains `v1alpha1`. Its implementation evidence
date is `2026-10-22`; the documentation was rechecked on `2026-10-23` without
changing the accepted target roots.

| Provider | Selected target | Reviewed portable contract |
| --- | --- | --- |
| Codex | `.agents/skills/SKILL_ID/SKILL.md` | A skill is a directory anchored by `SKILL.md` with `name` and `description` frontmatter followed by instructions. The shared root requires file-level ownership. |

| OpenCode | `.opencode/skills/SKILL_ID/SKILL.md` | The native project root accepts `SKILL.md` with required `name` and `description`; compatible roots are discoverable but are not selected for ownership. |

A later provider-documentation change does not silently change generated

## 4. Pilot and workspace fixture

D1 creates a fresh disposable workspace for every provider and test case. The
workspace is assembled through the public composition and provider-sync
surfaces rather than by copying an expected provider package into place.

The baseline fixture contains:

- the embedded `engineering-toolkit@0.2.1` catalog;
- `go-service@0.1.0` selected explicitly;
- `project_name` bound to one fixed portable value;
- the rendered canonical `project-guide@0.1.0` package;
- one unrelated provider-native package in each provider root;
- one official-style `speckit-*` package in the shared Codex root;
- sentinel files outside all selected output paths; and
- initialized `.engkit` state with no pre-existing provider ownership.

Fixture bytes, names, permissions used for assertions, and expected SHA-256
digests are repository-owned test data. They contain no credentials, provider
configuration, downloaded upstream content, or executable resources. The
Spec Kit sentinel is a minimal ownership fixture, not a vendored copy of Spec
Kit.

## 5. D1 offline conformance layers

### 5.1 Static contract validation

For each provider, validate the exact rendered `SKILL.md` before publication:

- the target path equals the accepted adapter target;
- the file begins with unambiguous YAML frontmatter;
- `name` equals both `project-guide` and its directory name;
- `description` is present and equals the canonical description;
- no unsupported top-level provider field is introduced;
- the Markdown body equals normalized canonical instructions;
- line endings and the final newline are deterministic; and
- the file digest equals the approved golden digest.

Golden bytes are reviewed fixtures. Regeneration is never an automatic test
update; a changed digest must fail until the adapter change is reviewed.

### 5.2 Transaction lifecycle validation

For each provider, exercise this sequence in a new disposable workspace:

1. plan project creation and apply the exact approved composition plan;
2. validate the installed canonical pilot;
3. build the provider sync plan twice and compare plan IDs and output digests;
4. apply the exact approved sync plan;
5. rebuild the plan and require an `unchanged` result;
6. validate the provider file and ownership record against live bytes;
7. build and apply the exact approved unsync plan;
8. prove that owned output is absent, the live ownership record is absent, and
   retained evidence is complete; and
9. prove that canonical, provider-native, Spec Kit, and sentinel bytes did not
   change.

The harness uses public CLI routing for end-to-end cases and focused Go tests
for failure injection. It never invokes a provider runtime.

### 5.3 Refusal and isolation validation

The matrix must cover:

- selecting one provider creates no output or ownership for either other
  provider;
- unowned existing output is preserved and blocks execution;
- changed owned output is preserved and blocks sync and unsync;
- symbolic links, Windows junctions, special files, path-type conflicts, and
  case collisions fail closed;
- stale approval fails after canonical, target, or ownership state changes;
- scripts, non-empty permission requests, unresolved dependencies, and lossy
  mappings remain non-executable;
- malformed, linked, overlapping, or unreadable ownership evidence blocks the
  operation;
- canonical mutation remains blocked while any provider ownership is present;
- lock contention and ambiguous recovery preserve all evidence; and
- no operation changes `.specify`, `speckit-*`, `AGENTS.md`, `CLAUDE.md`,
  provider policy, or unrelated provider files.

Existing C2 unit and failure-injection tests may satisfy a case when they run
on the target platform and assert the same externally visible boundary. D1 adds
only missing integration, portability, and pilot-specific coverage.

## 6. Platform matrix and equivalence

D1 uses the same six targets as the release-candidate workflow:

| Operating system | Architecture |
| --- | --- |
| Windows | AMD64 |
| Windows | ARM64 |
| Linux | AMD64 |
| Linux | ARM64 |
| macOS | AMD64 |
| macOS | ARM64 |

Every target must run the native binary and the same conformance scenario. For
the fixed pilot and baseline fixture, all targets must produce identical:

- canonical package digest;
- rendered `SKILL.md` bytes and digest;
- sorted relative output paths and mapping findings; and
- ownership source and output fields other than the root-bound synchronization
  plan ID.

Transaction-local timestamps, absolute temporary roots, journal event IDs tied
to a plan, root-bound plan and synchronization IDs, and platform path separators
may differ only where their existing contracts already define them as
operational evidence. A plan ID must repeat exactly when rebuilt in the same
unchanged workspace, but it is not compared across different absolute roots.
These operational differences must not alter rendered bytes, relative paths,
mapping findings, or generated-file digests.

## 7. Evidence and pass criteria

D1 produces ordinary test output and uploaded CI logs, not a new public or
persisted Engineering Toolkit schema. The implementation review must include:

- the exact source commit and Go version;
- runner operating system and architecture;
- provider contract version and evidence date;
- pilot catalog, profile, template, and canonical package digests;
- provider plan IDs and rendered output digests;
- pass/fail status for every matrix case;
- confirmation that no provider runtime or network was invoked; and
- the exact CI workflow run used as release evidence.

D1 passes only when all six targets pass every mandatory case and their
portable projections compare equal. A skipped platform, unsupported filesystem
primitive, changed golden output, provider-contract ambiguity, or preservation
failure blocks the gate.

## 8. D2 native discovery smoke

D2 execution remains unauthorized. The draft
[`D2 native-discovery approval packet`](provider-native-discovery-d2.md)
separates local inventory from provider smoke execution. Before execution, its
provider record must contain, for each provider:

- exact provider name and installed version;
- supported host operating systems and architectures;
- exact read-only or bounded discovery command;
- whether authentication, subscription, credentials, or network access is
  required;
- whether the command can execute tools, scripts, or repository instructions;
- disposable workspace, prompt, timeout, output capture, and cleanup method;
- expected discovery evidence and pass/fail rule; and
- rollback or uninstall procedure for anything installed for the smoke test.

The preferred check proves only that the provider discovers the generated
`project-guide` metadata and can load its instructions. It must not ask the
provider to modify files, execute the skill workflow, contact external systems,
change provider configuration, initialize Spec Kit, or adopt ownership.

Native discovery results are provider-version-specific evidence. They do not
replace D1, change the canonical package, or grant future provider access.

The draft packet contains unresolved version and command fields. It authorizes
neither D2-I inventory probes nor D2-S native discovery until their exact
inputs receive separate approval.

## 9. Non-goals

`v0.2.2D` does not:

- add a provider SDK, library, or runtime dependency;
- generate `CLAUDE.md`, provider commands, hooks, permission policy, or config;
- execute skill scripts or resolve skill dependencies;
- download, initialize, upgrade, remove, or run Spec Kit;
- test model quality or automatic skill-selection accuracy;
- add remote catalogs, marketplace installation, or hosted evaluation;
- change canonical, plan, ownership, journal, checkpoint, or result schemas;
- change the public CLI contract;
- clean retained backups or empty provider directories; or
- authorize a commit, push, tag, release candidate, or stable release.

## 10. Implemented D1 surface

The approved D1 implementation adds:

- an exact reviewed golden `SKILL.md` and focused contract, refusal, collision,
  and lifecycle tests in `internal/providersync` and `internal/providersyncexec`;
- `scripts/test-provider-conformance.ps1`, which composes the embedded pilot and
  exercises sync, unchanged replay, ownership verification, and unsync with the
  native release binary in disposable workspaces;
- `scripts/compare-provider-conformance.ps1`, which requires all six runtime
  records and byte-identical portable projections; and
- provider-conformance execution and evidence aggregation in the existing
  release-candidate matrix.

The evidence files are private test artifacts rather than a public Engineering
Toolkit schema. The implementation adds no production package and does not
change the public CLI contract.

Focused static contract tests, PowerShell syntax checks, and a synthetic
six-platform evidence comparison pass locally. Windows sandbox policy prevents
the local end-to-end harness from exercising the executor's required atomic
no-replace primitive, and the sandbox lacks symbolic-link privilege. Those
local restrictions were not treated as waivers: the required native scenarios
passed on all six GitHub-hosted release targets, including macOS temporary-root
normalization, and the aggregate portable-evidence comparison passed.

The stable evidence is GitHub Actions run `39977017785` at commit
`25c14d88e9871b78d674956d370a84768db9b90e`. The immutable `v0.2.2` release
contains 12 uploaded assets whose digests match the reviewed package manifest
and checksum file.

## 11. Rollback

D1 rollback removes only its fixtures, focused conformance tests, orchestration
scripts, CI wiring, and implementation milestone context, then restores this
document and the roadmap to their planning-only state. It must not rewrite
transaction evidence or delete user/provider content from any real workspace.
